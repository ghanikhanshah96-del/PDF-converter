# **Client-Side PDF Content Stream Modification and Reflow Architecture**

The most viable free, 100% client-side design for a commercial web application that genuinely mimics Adobe Acrobat’s "Edit PDF" functionality relies on a bifurcated hybrid architecture: it utilizes a WebAssembly (WASM) build of PDFium (licensed under BSD-3-Clause) purely for high-fidelity rendering and precise glyph-level coordinate extraction, paired with pdf-lib (MIT) and @pdf-lib/fontkit (MIT) to manually decompress, parse, mutate, and re-serialize the PDF’s underlying /Contents stream byte array. When a user edits a paragraph, the engine decodes the stream, mathematically isolates the Tj or TJ operators at the cursor coordinates, and physically deletes or modifies those strings within the PDF structure rather than merely covering them with a white HTML overlay. The engine then computes a local bounding box, implements rudimentary line-wrapping logic, and writes new text operators into the stream using a bundled open-source fallback font. The exact Acrobat behaviors this architecture still cannot achieve include true document-wide structural reflow (pushing text across page boundaries), accurately recalculating intersecting complex vector paths or gradient meshes underneath deleted text, and, most critically, preserving and reusing the original embedded subset fonts for newly typed characters, as the required bezier curves for absent glyphs physically do not exist within the document and cannot be synthesized by the browser.

## **The Architectural Reality of Portable Document Formats**

The Portable Document Format (ISO 32000\) was never designed as a structural document standard like HTML or Microsoft Word's OOXML. It is fundamentally a fixed-layout graphics state machine intended for reliable final-form presentation1. Modern commercial web platforms seeking to build in-browser PDF editors frequently fall into the trap of treating PDFs as DOM trees.  
The text in a PDF document does not exist as paragraphs or flowing containers. It is represented by a sequence of highly specific drawing operators encapsulated within BT (Begin Text) and ET (End Text) blocks3. An operator like Tj (show text) or TJ (show text with individual glyph positioning) is fed a string of bytes3. Before this text is drawn, the PDF engine establishes a Current Transformation Matrix (cm) and a Text Matrix (Tm), which dictate the exact mathematical placement, rotation, and scaling of the glyphs on the canvas3.  
Furthermore, the strings passed to these operators are rarely plain ASCII text. In almost all documents generated by modern software (Chrome, Word, LaTeX), the fonts are subset1. Subsetting means the document only embeds the specific glyph outlines utilized in the text. For example, if a document contains only the word "Document", the embedded font file lacks the vector data for the letter "a"5. To map the text back to characters, the PDF relies on a /ToUnicode CMap, frequently using an Identity-H encoding where the literal characters in the stream are actually 2-byte hex indices corresponding to the subset array (e.g.,  instead of (Docu))3. This structural reality dictates the absolute limits of client-side editing.

### **The Commercial SDK Ceiling**

When analyzing the capabilities of paid commercial SDKs such as Nutrient (formerly PSPDFKit), Apryse (formerly PDFTron), and Adobe's own PDF Embed Services, it is crucial to understand why they succeed where free libraries fail. These commercial entities do not rely on pure JavaScript parsers. They compile massive, proprietary C++ rendering and typesetting engines (such as Adobe's AGM or Apryse's Core) into WebAssembly8.  
When a user edits text in Acrobat or Apryse, the proprietary engine performs "content normalization." It parses the raw content stream into an internal Document Object Model, analyzes the geometric proximity of glyphs to deduce paragraphs, and allows the user to mutate this internal model8. When synthesizing missing characters for a subset font, these commercial engines leverage their access to vast cloud-based font libraries or the user's operating system to silently drop the subset font and re-embed a full version of the font (e.g., Arial or Helvetica)9. Free, 100% client-side web tools inherently lack the licensing to bundle these proprietary fonts and lack the filesystem access to steal them from the user's OS10. Therefore, paid SDKs represent a technological ceiling that open-source client-side solutions can approximate, but never perfectly replicate.

## **Evaluation Framework: The "Adobe-Like" Parameters**

To rigorously assess the open-source landscape, each repository and library must be evaluated against ten strict parameters that define an "Adobe-like" experience. Each parameter is scored on a scale of 0 to 5\.  
**1\. In-Place Text Editing (0-5):** A score of 0 indicates the tool uses absolute CSS overlays or PDF.js FreeText annotations, which merely append /Type /Annot objects to the page's /Annots array without modifying the /Contents stream11. A score of 5 requires the engine to parse the byte array, locate the Tj operator, and physically rewrite or delete the bytes.  
**2\. Font Preservation and Glyph Widths (0-5):** A score of 0 indicates the tool indiscriminately replaces all edited text with Helvetica or a standard base-14 font. A score of 5 indicates the tool can parse /FontDescriptor widths, maintain kerning, and gracefully fallback when encountering an Identity-H CMap or a broken /ToUnicode table13. Subsets mathematically cannot be appended to without the source font5.  
**3\. Paragraph Reflow (0-5):** A score of 0 indicates the tool relies on a "white box" approach—drawing a background-colored rectangle over the old glyphs and stamping new text on top without adjusting surrounding lines15. A score of 5 means the engine geometrically groups text objects into logical blocks and dynamically recalculates line breaks and Tm offsets for subsequent lines.  
**4\. Image Manipulation (0-5):** A score of 0 indicates images are permanently flattened. A score of 5 indicates the ability to parse /XObject references, alter their transformation matrices (cm) to move or resize them, and delete their references from the stream.  
**5\. Vector Editing (0-5):** A score of 0 means paths (lines, bezier curves, table borders) are untouchable. A score of 5 means the tool can parse m (move to), l (line to), and c (curve to) operators to manipulate shapes3.  
**6\. Scanned Pages and OCR (0-5):** A score of 0 means the tool fails on scans. A score of 5 implies an integrated WASM OCR engine capable of generating invisible text layers. The inclusion of Arabic support is critical, though Tesseract.js language data for Arabic (ara.traineddata) is notoriously large and resource-intensive17.  
**7\. Normal PDF Export (0-5):** A score of 0 indicates the tool rasterizes the entire page into a JPEG, destroying selectability and ballooning file size. A score of 5 requires the tool to serialize a mathematically sound PDF where unedited text remains perfectly selectable and rotations (/Rotate) are respected2.  
**8\. Encryption Preservation (0-5):** A score of 0 means the tool strips security handlers (RC4/AES) and saves plaintext20. A score of 5 means the tool can decrypt the stream for editing and seamlessly re-encrypt the mutated stream upon serialization.  
**9\. Mobile-Ready Layout (0-5):** A score of 0 represents the current flawed implementation: a fixed \~900px render at 0.85 zoom. A score of 5 requires responsive CSS, devicePixelRatio canvas scaling, pinch-to-zoom via CSS transforms, and precise coordinate mapping between the touch event and the unscaled PDF user space.  
**10\. Speed and Architecture (0-5):** A score of 0 indicates heavy main-thread blocking, massive memory leaks, or forced downloads of 50MB+ WASM binaries. A score of 5 requires Web Worker offloading, minimal bundle sizes, and rapid instantiation for 50+ page documents.

## **Comprehensive Analysis of Evaluated Solutions**

The following analysis scrutinizes the requested repositories and libraries, unmasking their underlying architectures and scoring them against the stringent commercial and technical constraints of the project.

### **The "AI-Powered" Faux Editors**

**aliabbas12512/AI-PDF-SBT-EIDTOR (lumenpaper branch)** This repository is an instructional demonstration of how to build a web application, not a functional PDF content stream editor21. The architecture relies on rendering the PDF to a background image using pdfjs-dist. It then utilizes Fabric.js (a canvas library) to allow users to draw text and shapes on top of this background21. To "edit," it uses an inpainting technique to erase the underlying pixels and overlays Fabric.js text objects. Finally, it uses pdf-lib to reconstruct the PDF by embedding the inpainted image and drawing the new text on top21.

* *Flaws:* This completely destroys the vector nature of the original PDF. All original text becomes an unselectable rasterized image. Embedded fonts are obliterated. The repository's own readme admits that original fonts are replaced, vectors are flattened, bidirectional text is merely approximate, and mobile functionality is untested21.  
* *Scores:* Text Edit (0), Font (0), Reflow (0), Images (0), Vectors (0), OCR (0), Export (0), Encryption (0), Mobile (0), Speed (1).  
* *Verdict:* A complete failure for commercial deployment. The "lift text, inpaint holes, Fabric canvas" methodology is merely a visual demo and entirely unsuitable for a professional product.

**mudasaranabitech-crypto/PDF-eidtor** This project represents a fundamental misunderstanding of client-side architecture. It is a Vite application that relies heavily on a Node.js backend (Express) and requires a GEMINI\_API\_KEY to function22. The system uploads the PDF, extracts the text, sends it to a Large Language Model (Gemini or OpenAI) to detect and correct grammar, and highlights the changes22.

* *Flaws:* It directly violates the strict privacy rule established for the current infrastructure, which dictates that files must not be uploaded and no API keys can be used in the edit path23. Furthermore, passing extracted text to an LLM does not correlate to structurally rewriting the PDF's Tj operators22.  
* *Verdict:* Disqualified due to server-side dependencies, LLM reliance, and privacy violations.

### **The Annotation Overlays**

**hikashop-nicolas/pdfedit** This repository is a basic Vue/JavaScript wrapper around pdf.js25. It focuses on adding text, shapes, and images to a document26.

* *Flaws:* The codebase clearly indicates that it functions as an annotation tool26. When a user "edits," they are simply placing a new object over the existing canvas. The repository does not contain a custom stream parser to rewrite the /Contents byte array. The claim of "reusing original glyph codes" refers to attempting to map keyboard input to extracted text layers, but without mutating the underlying stream, the exported document simply contains the original text hidden beneath the new text26.  
* *Scores:* Text Edit (0), Font (0), Reflow (0), Images (0), Vectors (0), OCR (0), Export (3), Encryption (1), Mobile (2), Speed (3).  
* *Verdict:* This is essentially what the current "Edit PDF" tool already does. It does not solve the core requirement of true content stream editing.

**dean9703111/pdf-editor** A single-file browser PDF editor utilizing HTML, JavaScript, pdf.js, and pdf-lib27. It supports annotations, highlights, and local export.

* *Flaws:* Similar to the Hikashop repository, this project utilizes HTML overlays positioned above the pdf.js canvas27. While it correctly utilizes pdf-lib for client-side serialization, it makes no attempt to decode and splice the content stream. It operates strictly on the principle of adding new data to the document, not mutating existing data.  
* *Verdict:* Disqualified for failing to edit existing content streams.

**Mozilla pdf.js FreeText Annotation Editor** Recent pull requests and issues within the official Mozilla pdf.js repository (e.g., issues 2045168 and 16278\) highlight the addition of a FreeText annotation editor28.

* *Flaws:* pdf.js is a viewer, not a serializer30. The FreeText editor allows users to type text onto the page, which the viewer then serializes as a /Type /Annot /Subtype /FreeText object in the page's /Annots array11. It generates an Appearance Stream (/AP) for the annotation so other viewers can render it11. However, this *does not touch the existing content stream*. If you place a FreeText annotation over existing text, the existing text remains entirely intact and selectable underneath the annotation11.  
* *Verdict:* Recommending pdf.js annotations as an "editor" is fundamentally incorrect for a tool promising Acrobat-like manipulation of existing text.

### **The Content Stream Manipulators**

**kuldeepcodes/pdfstudio** This repository represents the most technically honest attempt at pure JavaScript content stream editing16. It utilizes pdf.js for rendering and pdf-lib for serialization, but crucially, it includes a custom stream parser16.

* *Mechanics:* To remove old text, the engine decodes the page's content stream, scans for string tokens inside Tj or TJ arrays, matches them against the line being replaced, and explicitly deletes those tokens from the stream16. This means the original text is genuinely removed from the file.  
* *Flaws:* The engine admits defeat when faced with subset fonts utilizing an Identity-H CMap16. Because it cannot locate the literal string in the encoded stream, it falls back to drawing a background-colored box over the text and stamping new text on top16. Furthermore, it handles structural edits line-by-line and does not reflow multi-line paragraphs16. It explicitly lacks OCR capabilities16.  
* *Scores:* Text Edit (3), Font (1), Reflow (0), Images (2), Vectors (0), OCR (0), Export (4), Encryption (1), Mobile (1), Speed (2).  
* *Verdict:* A brilliant proof-of-concept for stream token blanking, but its fallback to white-boxing on subset fonts (which comprise 90% of modern PDFs) and lack of reflow make it insufficient as a standalone solution for a premium commercial tool.

**bevinkatti/PdfZero** An open-source, client-side editor utilizing pdf.js, pdf-lib, and Tesseract.js15.

* *Mechanics:* It utilizes a layered editing model. It extracts text runs, transforms, and baselines from pdf.js, positions editable DOM text over the raster, and samples the local background to hide the original text15. On export, it uses pdf-lib to write background patches and replacement text, attempting to fit the new text into the original run width using character spacing adjustments15.  
* *Flaws:* The author explicitly notes that true high-level editing for embedded subset fonts or background reconstruction requires a real PDF engine like PDFium or MuPDF15. The background patching method is susceptible to failure on complex gradients. The integration of Tesseract.js for OCR is highly memory-intensive in a browser environment18.  
* *Scores:* Text Edit (2), Font (1), Reflow (0), Images (3), Vectors (0), OCR (3), Export (3), Encryption (2), Mobile (3), Speed (2).  
* *Verdict:* A highly capable overlay tool, but it suffers from the same structural limitations as the current deployed product. The text is not truly manipulated at the stream level; it is merely patched over.

### **The Compiled WASM Engines**

**open-pdf-edit/OpenPdfEdit** A desktop application built with Rust and PDFium, compiled to WebAssembly31.

* *Mechanics:* It offers a complete offline editing experience, including annotations, text editing, and form filling32. Because it leverages PDFium directly, it has access to lower-level stream manipulation functions32.  
* *Flaws:* It is architected as a desktop application (Windows/macOS) and Chrome extension, not a pure web library deployable in a Next.js environment31.  
* *Verdict:* Out of scope for immediate web deployment, though its utilization of PDFium points toward the correct architectural path.

**PDFCraftTool/pdfcraft** A highly capable, privacy-focused PDF toolkit that runs entirely in the browser using WebAssembly33.

* *Mechanics:* It offers over 90 professional tools and features a visual workflow editor33. It handles stream editing and rendering directly via its compiled engine35.  
* *Flaws:* The project is licensed under the **GNU Affero General Public License v3.0 (AGPL)**33.  
* *Verdict:* Disqualified. The AGPL license mandates that any web service utilizing the software over a network must make its entire surrounding source code open and available36. This is incompatible with a proprietary commercial website.

**QrCommunication/gigapdf** A self-hostable WYSIWYG editor powered by an in-house Rust-to-WebAssembly engine (gigapdf-lib)37.

* *Mechanics:* It reads and rewrites the content stream directly, reflows paragraphs, handles Identity-H ToUnicode CMaps, and avoids cosmetic overlays37. It represents exactly the functionality requested.  
* *Flaws:* It is licensed under the **PolyForm Noncommercial 1.0.0** license37. The documentation explicitly states that commercial licensing is available separately37.  
* *Verdict:* Disqualified. The PolyForm Noncommercial license strictly prohibits use in a commercial product without a paid agreement38.

**mupdf.js (Artifex)** The official Javascript/WASM binding for the MuPDF engine, built by Artifex Software39.

* *Mechanics:* MuPDF is an incredibly fast, highly accurate C-based engine capable of deep stream manipulation, rendering, and text extraction39.  
* *Flaws:* Like PDFCraft, MuPDF is dual-licensed under the **AGPL** and a commercial license39.  
* *Verdict:* Disqualified for the same licensing contagion reasons as PDFCraft.

### **The Clear Winner: BSD-Licensed PDFium WASM wrappers**

Given the strict rejection of AGPL and PolyForm licenses, the only mathematically sound path to extracting precise text coordinates and manipulating documents without risking the commercial proprietary nature of the Next.js site is utilizing a **BSD-licensed WebAssembly build of PDFium**, such as hyzyla/pdfium or urish/pdfium-wasm42.  
Google's PDFium (the engine behind Google Chrome's PDF viewer) is written in C++ and handles complex Identity-H CMaps, matrix transformations, and kerning calculations flawlessly44. While PDFium's public API is primarily geared toward viewing and text extraction, it exposes FPDFText\_GetCharBox, which provides the exact unscaled coordinates of every printed character44. This solves the mobile layout crisis: by decoupling the visual render from the DOM overlay, coordinates extracted by PDFium remain accurate regardless of how the CSS scales the canvas on a mobile viewport.  
For the serialization phase, the architecture must rely on pdf-lib (MIT). While pdf-lib lacks a high-level text editing API, its PDFRawStream and decodePDFRawStream functions allow a developer to extract the page stream, run a custom AST parser to delete specific Tj tokens (as demonstrated by pdfstudio), and rewrite the stream46.

## **Implementation Plan: Next.js App Router Architecture**

The implementation of a true "Adobe-like" redact-and-replace editor requires a sophisticated orchestration of WASM workers, DOM layers, and byte-array serialization within the existing Next.js 15 / React 19 architecture.

### **1\. What to Leave Alone**

* **The ZetaOffice/ZetaJS WASM Engine:** The existing Word→PDF converter is structurally isolated. Its reliance on writer\_pdf\_Export and IndexedDB caching is highly optimized for document generation. Crucially, the stringent Cross-Origin-Opener-Policy (COOP) and Cross-Origin-Embedder-Policy (COEP) headers required for SharedArrayBuffer memory access in the Zeta engine must remain scoped exclusively to the /word-to-pdf-converter-free route48. Implementing these headers globally across the Next.js App Router would critically break third-party analytics, ads, or authentication scripts on the rest of the commercial site. Do not touch this engine.

### **2\. The Required Tech Stack**

* **PDFium WASM (**@hyzyla/pdfium **or custom build):** Licensed under BSD-3-Clause, this replaces pdf.js for rendering and extraction. PDF.js is notoriously slow at calculating bounding boxes for complex layouts and rotated text13. PDFium offers native C++ text extraction bindings that are highly performant44.  
* **pdf-lib:** Maintained for document serialization, specifically utilizing its ability to decode and re-encode /Contents streams (decodePDFRawStream)46.  
* **@pdf-lib/fontkit:** Essential for registering custom fallback fonts when subset font re-hydration inevitably fails50.

### **3\. Step-by-Step Editor Pipeline**

#### **Phase A: Decoupled Rendering and Extraction (PDFium)**

> 1. **Dynamic Import:** In Next.js 15, WASM modules must be strictly isolated from Server-Side Rendering (SSR). Use next/dynamic with ssr: false to load the PDFium worker51.  
> 2. **Resolution-Independent Rendering:** To solve the current \~900px mobile flaw, pass the document to the PDFium worker and render the page to an OffscreenCanvas at window.devicePixelRatio.  
> 3. **Coordinate Mapping:** Query PDFium for the exact bounding box of every character. Create an overlay div absolutely positioned over the canvas. Translate the PDFium coordinates (which are in standard PDF points, 72 DPI) into CSS percentages relative to the page width. This ensures that when a user pinch-zooms on a mobile device, the editable text hotspots scale perfectly with the canvas via CSS transform: scale(), without requiring constant WASM re-rendering.

#### **Phase B: Stream Mutation (**pdf-lib**)**

> 1. When a user taps a text span, generate a contenteditable div constrained by the paragraph's bounding box.  
> 2. Upon deselection (commit), load the document bytes into pdf-lib52.  
> 3. Extract the specific page's /Contents stream46.  
> 4. Decompress the stream. Write a targeted AST parser to iterate through the string. Track the Current Transformation Matrix (cm) and Text Matrix (Tm) to map stream coordinates to the physical coordinates edited by the user3.  
> 5. Locate the specific Tj or TJ operator responsible for the original text3.  
> 6. **The Surgical Strike:** Unlike PdfZero which paints a white box, mathematically delete the targeted hex indices or literal strings from the operator array15. For example, mutate \[(Hello) 20 (World)\] TJ to \[(World)\] TJ. This guarantees the exported PDF is clean and does not contain hidden overlapping text16.

#### **Phase C: Reflow and Re-insertion**

> 1. Read the newly typed text from the DOM.  
> 2. Because the original font is almost certainly an Identity-H subset, it cannot be appended to1. Instead, instantiate an ArrayBuffer containing a metrically similar, open-source Google Font (e.g., Open Sans for sans-serif).  
> 3. Register the font via pdfDoc.embedFont(fontBytes, { subset: true })52.  
> 4. Calculate line breaks using the new font's advance widths.  
> 5. Append new BT ... ET blocks containing the new Tm matrices and Tj strings to the end of the content stream3.  
> 6. Serialize and trigger the download.

### **4\. Expected Failure Cases and Mitigations**

* **Subset Fonts (**Identity-H**):** The engine will fail to type new characters in the original font4. **Mitigation:** The UI must be honest. When editing begins, flash a brief notification ("Font substituted for editing") and immediately swap the DOM text to the fallback font. Do not attempt to reverse-engineer the /ToUnicode map, as the bezier curves for new glyphs simply do not exist in the file5.  
* **Columns and Layout:** The geometric heuristic used to group lines into paragraphs will frequently misinterpret two adjacent columns as a single horizontal line if their baselines align perfectly. **Mitigation:** Implement a strict vertical gutter threshold. If the horizontal X gap between two text runs exceeds 300% of the calculated space character width, forcefully split them into separate bounding boxes.  
* **Arabic and RTL:** pdf-lib lacks a native HarfBuzz shaping engine. Typing Arabic will result in disconnected, left-to-right letters. **Mitigation:** Integrate a lightweight JavaScript Arabic reshaper (such as the logic found in jsPDF's processArabic) to convert Unicode strings into their contextual presentation forms (initial, medial, final) before passing them to pdf-lib53.  
* **Encrypted Files:** If a user uploads a password-protected PDF (AES-256), pdf-lib can decrypt it for editing if the password is provided20. However, structural mutations often break complex security handlers upon re-saving. **Mitigation:** Intercept the save event, alert the user that editing modifies the file structure, and export the file unprotected. Never silently copy ciphertext or save an unprotected file without explicit user consent20.  
* **Scans (No Text Stream):** If PDFium extracts zero text objects, the page is a flattened image. **Mitigation:** Alert the user. If OCR is strictly required, instantiate tesseract.js in a Web Worker. Be highly cautious: Tesseract language packs (especially Arabic ara.traineddata) can exceed 30MB17. Instantiate the worker, process the bounding box, and immediately call worker.terminate() to prevent severe memory leaks that crash iOS Safari tabs18.

### **5\. Headless Testing Strategy**

Never test PDF mutation relying on visual screenshots (Puppeteer/Playwright), as a white-box overlay looks identical to a structurally deleted token on a rasterized canvas.

> 1. **Assertion 1:** After the automated test edits "Old Text" to "New Text" and exports the file, run the exported file through pdf.js's headless getTextContent() API10. Assert that the array of text items contains exactly zero instances of "Old Text".  
> 2. **Assertion 2:** Assert that the array contains exactly one instance of "New Text" at the correct transform coordinates.  
> 3. **Assertion 3:** Utilize a low-level diagnostic tool like mutool info to inspect the exported byte stream, asserting that the new /Font dictionary was correctly embedded and that no undefined glyph indices (Tofu boxes) were written to the stream55.

## **The "Do Not Build" List**

To ensure the commercial viability, performance, and legal safety of the web application, strictly avoid the following methodologies:

> 1. **Do not build with AGPL, GPL, or PolyForm Licenses:** Reject mupdf.js, PDFCraft, and GigaPDF entirely35. Linking to or modifying these libraries requires open-sourcing the proprietary commercial website's surrounding Next.js code or violates non-commercial clauses, inviting severe legal liability36.  
> 2. **Do not use LLMs, Gemini, or OpenAI for text reflow:** Frameworks that extract text, pass it to an LLM for "grammar fixing," and attempt to rewrite the PDF (e.g., PDF-free-editor) violate the "No API Keys / No Uploads" privacy rule and introduce unacceptable, asynchronous latency into a UI that expects instant typing feedback22.  
> 3. **Do not build CSS/Fabric.js Raster Overlays:** Do not fall back to the AI-PDF-SBT-EIDTOR methodology of rasterizing the PDF to a JPEG, overlaying an HTML \<canvas\>, drawing text using Fabric.js, and flattening the whole result into an image-based PDF. This destroys all existing vectors, bloats file sizes exponentially, and results in completely unselectable text21.  
> 4. **Do not attempt to write a full C++ layout engine in JavaScript:** Relying on pdf-lib to write strings via drawText is the performance ceiling for pure JavaScript. Attempting to port a complex typesetting engine to calculate true Acrobat-style flowing text that pushes paragraphs across multiple page boundaries will stall development indefinitely and crash browser threads. Rely strictly on localized, single-page bounding-box edits.  
> 5. **Do not implement continuous WASM live-rendering:** Calling PDFium's render functions on every keystroke will lock the main thread and destroy mobile battery life. Edits must occur exclusively in the lightweight, transparent HTML DOM layer. The heavy WASM/pdf-lib serialization pipeline should only be invoked once, when the user unfocuses the text box or clicks the export button, committing the structural changes to memory.
